# 1주차 백엔드 키워드 정리

> 서비스 맥락: 지역별 가게 방문 미션을 수행하고, 지역마다 10개를 완료하면 1,000 Point를 받는 리워드 서비스

## PK, FK란?

- **PK(Primary Key)** 는 테이블의 행 하나를 유일하게 식별하는 키다. 중복과 `NULL`을 허용하지 않는다. 예를 들어 `member.id`가 PK라면 두 회원이 같은 `id`를 가질 수 없다.
- **FK(Foreign Key)** 는 다른 테이블의 PK 또는 `UNIQUE` 컬럼을 참조하는 컬럼이다. 예를 들어 `store.region_id`가 `region.id`를 참조하면 존재하지 않는 지역에 가게를 연결하는 데이터를 막을 수 있다. 이런 규칙을 **참조 무결성**이라고 한다.

## ERD란?

**ERD(Entity Relationship Diagram)** 는 서비스 데이터를 엔티티, 속성, 관계로 나누어 시각화한 설계도다. 테이블과 컬럼만 나열하는 것이 아니라 데이터가 어떻게 연결되는지와 관계의 개수(카디널리티)를 확인한다.

이번 미션에서는 `member`, `region`, `store`, `mission`을 핵심 엔티티로 두고, 회원의 미션 수행 상태는 `member_mission` 관계 테이블에 저장한다.

## 연관관계란? 어떻게 설정하는가?

연관관계는 엔티티 사이의 의미 있는 연결이다. 먼저 양쪽에 몇 개씩 연결될 수 있는지 확인하고, 그 결과에 따라 FK 위치와 제약조건을 정한다.

| 관계 | 구현 방법 | 이번 미션의 예 |
| --- | --- | --- |
| 1:1 | 한쪽에 FK를 두고 `UNIQUE` 제약조건을 둔다. | 회원 설정을 별도 테이블로 분리하는 경우 |
| 1:N | N 쪽 테이블에 1 쪽의 PK를 FK로 저장한다. | `store.region_id` |
| N:M | 두 FK를 가진 중간 매핑 테이블을 둔다. | `member_mission` |

1:N에서 FK는 여러 개가 생기는 쪽에 둔다. 따라서 `region`에 `store_id` 목록을 저장하지 않고, 각 `store`가 하나의 `region_id`를 가진다. 한 컬럼에 여러 값을 넣지 않아도 되고 지역별 가게 조회도 명확해진다.

N:M에서는 매핑 테이블도 중요한 엔티티다. `member_mission`에는 두 FK 외에 `status`, `started_at`, `completed_at`처럼 “한 회원이 한 미션을 수행한 상태”를 저장한다. 관계에 속한 정보는 관계 테이블에 두는 것이 자연스럽다.

## 정규화란?

정규화는 중복과 갱신 이상을 줄이도록 테이블을 의미 있는 단위로 나누는 과정이다.

- **1NF**: 한 칸에는 하나의 원자값만 둔다. `mission_id`에 `1, 2, 3`처럼 여러 값을 문자열로 저장하지 않는다.
- **2NF**: 복합키를 쓸 때 모든 일반 컬럼이 복합키 전체에 의존하도록 한다.
- **3NF**: 일반 컬럼이 다른 일반 컬럼에 다시 의존하지 않도록 한다. 예를 들어 `store`에 `region_name`을 복사하지 않고 `region_id`로 `region`과 연결한다.

이 설계에서는 지역 이름을 `region` 테이블 한 곳에서 관리하므로 이름을 변경해도 일관성이 유지된다. 반대로 테이블이 나뉘면 조회 시 `JOIN`이 늘어날 수 있다.

## 반정규화란?

반정규화는 읽기 성능이나 조회 편의를 위해 일부 값을 의도적으로 중복 저장하는 방식이다. 예를 들어 미션을 완료한 회원 수를 매번 `member_mission`에서 세는 대신 `mission.completed_member_count`에 캐시할 수 있다.

하지만 원본과 복제값이 달라질 위험이 있다. 반정규화한다면 원본 데이터를 정하고, 미션 완료 처리와 카운터 갱신을 같은 트랜잭션에서 처리하거나 주기적으로 재계산해야 한다. 이번 미션 범위에서는 카운터를 저장하지 않고 `member_mission`을 기준으로 조회하는 편이 안전하다.

## DB에서 상속 관계는 어떻게 표현하는가?

객체지향의 상속을 관계형 DB로 표현하는 대표적인 방법은 다음과 같다.

1. **단일 테이블 전략**: 부모와 자식 속성을 하나의 테이블에 넣고 `type` 컬럼으로 종류를 구분한다. 조회는 쉽지만 사용하지 않는 `NULL` 컬럼이 늘 수 있다.
2. **조인 전략**: 공통 속성은 부모 테이블, 자식 속성은 별도 테이블에 둔다. 자식 테이블의 PK를 부모 PK이면서 FK로 사용한다. 중복은 적지만 조회에 `JOIN`이 필요하다.
3. **구체 테이블 전략**: 자식마다 독립 테이블을 만들고 공통 컬럼도 반복한다. 개별 조회는 단순하지만 공통 데이터가 중복된다.

이번 리워드 서비스에서는 가게와 미션에 상속 구조가 필요한 요구사항이 없으므로, 상속 테이블을 추가하지 않았다.

## 인덱스란?

인덱스는 원하는 행을 빠르게 찾기 위한 별도의 검색 구조다. 전체 테이블을 처음부터 읽는 대신, 조건에 맞는 데이터의 위치를 효율적으로 찾도록 돕는다.

이번 미션에서 고려할 인덱스는 다음과 같다.

- `store.region_id`: 특정 지역의 가게 목록 조회
- `mission.store_id`: 특정 가게의 미션 목록 조회
- `member_mission(member_id, status)`: 회원의 진행 중·완료 미션 조회
- `member_mission(member_id, mission_id) UNIQUE`: 같은 미션 중복 수행 방지

인덱스는 조회를 빠르게 하지만 저장 공간을 사용하고 `INSERT`, `UPDATE`, `DELETE` 때 함께 갱신된다. 따라서 모든 컬럼에 인덱스를 만들기보다 실제 `WHERE`, `JOIN`, `ORDER BY` 조건을 기준으로 고른다. PostgreSQL에서 PK를 선언하면 해당 키에는 유일한 B-tree 인덱스가 자동으로 만들어지지만, FK를 가진 참조 컬럼의 인덱스는 자동 생성되지 않으므로 조회 패턴을 보고 별도로 추가한다.
