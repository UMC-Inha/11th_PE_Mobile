# Chapter 04 키워드 정리

## 1. JPA / Hibernate와 TypeORM

> ORM과 구현체·라이브러리의 역할은 어떻게 다른가?

- **ORM**: 자바 객체를 DB 테이블처럼, 테이블을 객체처럼 다루게 해주는 기술이라는 **개념**입니다.
- **JPA**: 이 기술을 자바에서 어떻게 쓸지 정해 둔 **규칙서**라서, 그 자체로는 아무 일도 하지 않습니다.
- **Hibernate**: 실제로 SQL을 만들고 DB와 통신하는 일은 그 규칙대로 만들어진 **프로그램**인 Hibernate가 합니다.

## 2. Entity Lifecycle과 Persistence Context

> 엔티티를 저장할 때 즉시 SQL이 실행되지 않을 수 있는 이유는 무엇인가?

엔티티는 상태가 바뀌어 가는 일종의 **생애주기**를 가집니다.

| 상태 | 설명 |
| --- | --- |
| 비영속(new) | 처음 `new`로 만든 객체로, JPA가 전혀 모르는 상태 |
| 영속 | `persist()`로 저장하여 JPA가 관리하기 시작한 상태 |
| 준영속 | 관리가 끊긴 상태 |
| 삭제 | 삭제를 요청한 상태 |

영속 상태의 엔티티는 **영속성 컨텍스트**라는 임시 작업 공간에 보관됩니다. JPA는 저장 요청이 와도 바로 DB에 쓰지 않고, 실행할 SQL을 장바구니처럼 모아두었다가 트랜잭션이 끝날 때 한꺼번에 보냅니다.

- 이렇게 모아서 보내면 DB 왕복 횟수가 줄어듭니다.
- 객체 값만 바꿔도 JPA가 처음 상태와 비교해 바뀐 부분을 알아서 `UPDATE`해 줍니다.

즉 SQL이 늦게 실행되는 것은 버그가 아니라, **효율과 자동 변경 감지를 위한 설계**입니다.

> 예외적으로 ID를 DB가 만들어 주는 방식은 ID를 받아와야 하므로 저장 즉시 `INSERT`가 실행됩니다.

## 3. DTO와 API Contract

> Entity를 그대로 응답하면 어떤 문제가 생길까?

Entity는 DB 테이블 구조를 그대로 본뜬 객체입니다. 이를 응답으로 그대로 내보내면 여러 문제가 생깁니다.

1. **무한 반복**: 팀이 회원을, 회원이 팀을 서로 참조하고 있으면 JSON으로 바꾸는 과정에서 끝없이 서로를 따라가며 무한 반복에 빠집니다.
2. **민감 정보 노출**: 비밀번호처럼 보여주면 안 되는 필드도 함께 나갑니다.
3. **응답 형식 변경**: 가장 큰 문제는 DB 컬럼 이름 하나만 바꿔도 프론트가 받는 응답 형식이 바뀌어 화면이 깨진다는 점입니다.

API 응답 형식은 서버와 클라이언트 사이의 약속, 즉 **API Contract**입니다. 그래서 응답 전용 객체인 **DTO**를 따로 만들어 이 약속을 고정합니다. 이렇게 하면 내부 DB 구조는 자유롭게 바꿔도 외부에 보여주는 형식은 그대로 유지할 수 있습니다.

## 4. Validation

> 요청 검증을 Controller 단에서 수행해야 하는 이유는 무엇인가?

Controller는 외부 요청이 서버로 들어오는 **입구**입니다. 입구에서 "필수값이 비었나, 이메일 형식이 맞나, 길이가 적당한가" 같은 기본 검사를 하면, 잘못된 요청이 서비스나 DB까지 내려가기 전에 바로 돌려보낼 수 있습니다.

- 불필요한 DB 작업이 생기지 않습니다.
- 사용자에게도 서버 에러(`500`) 대신 요청이 잘못됐다(`400`)고 명확하게 알려줄 수 있습니다.
- 검사 규칙을 DTO에 어노테이션으로 선언해 두면, 서비스 코드에 `null` 체크 같은 방어 코드가 흩어지지 않습니다.

다만 모든 검사를 Controller에서 하지는 않습니다.

- "이미 가입된 이메일인가"처럼 DB를 확인해야 하는 규칙은 **서비스 계층**에서 검사합니다.
- DB의 `UNIQUE` 같은 제약은 **마지막 안전장치**로 둡니다.

## 5. N+1 Query

> 관계 데이터를 함께 조회할 때 쿼리가 예상보다 많이 실행되는 이유는 무엇인가?

팀 목록 10개를 조회한 뒤 각 팀의 회원을 하나씩 꺼내면, 팀마다 회원 조회 쿼리가 따로 나갑니다. 그래서 처음 1번에 팀 수 10번이 더해져 총 **11번**의 쿼리가 실행됩니다. 이렇게 데이터가 많을수록 쿼리 수가 함께 늘어나는 것이 **N+1 문제**입니다.

**해결 방법
- **fetch join**: 처음부터 팀과 회원을 한 번에 조인해서 가져옵니다.
- **batch size**: 회원을 `IN` 조건으로 묶어 한꺼번에 가져오도록 설정합니다.

## 6. Migration과 synchronize

> 운영 환경에서 자동 스키마 변경이 위험한 이유는 무엇인가?

`synchronize`는 엔티티 코드를 보고 DB 테이블 구조를 자동으로 맞춰 주는 기능입니다. 개발할 때는 편하지만, 운영에서는 다음과 같은 위험이 있습니다.

- 필드 이름을 바꾸면 ORM이 "기존 컬럼을 지우고 새 컬럼을 만들자"로 이해해서 **실제 데이터가 사라질 수 있습니다.- 언제 무엇이 바뀌었는지 기록도 남지 않아 문제가 생겨도 **되돌릴 수 없습니다.
그래서 운영에서는 자동 변경을 끄고, 변경 내용을 **마이그레이션 파일**로 작성해 검토한 뒤 순서대로 적용합니다. 코드 변경을 Git으로 관리하듯 DB 구조 변경도 버전 관리하는 방식입니다.
