# 8주차 백엔드 핵심 키워드

> 이 문서에서 **"직접 확인했다"**고 쓴 것은 이번 실습에서 실제로 실행해 본 것이고, 그렇지 않은 것은 개념 설명이다. 낙관적 잠금은 이번에 구현하거나 실험하지 않았다.

## 트랜잭션(Transaction)

여러 작업을 **한 덩어리**로 묶는 봉투다. 봉투 안의 작업은 모두 성공하거나, 하나라도 실패하면 모두 취소된다. 트랜잭션은 오류를 없애 주는 기능이 아니라, **오류가 났을 때 데이터가 어중간한 상태로 남지 않게** 해 주는 기능이다.

이번 `POST /movie-records`가 그 예다. "이 영화에 5점을 주고 즐겨찾기에도 넣기"는 사용자에게 하나의 행동이지만 서버에서는 두 테이블(`rating`, `favorite`)을 바꾼다.

```
트랜잭션 시작 → rating INSERT → favorite INSERT → commit
                                      └─ 여기서 실패하면 → rollback (rating도 되돌아감)
```

- **어디에 묶나**: `RatingService.create()`와 `FavoriteService.create()`를 **연달아 부르는 방식으로 끝내지 않는다.** 각자 별도의 트랜잭션으로 동작할 수 있어서, 앞의 것은 이미 commit되고 뒤의 것만 실패할 수 있다. "영화 기록"이라는 한 가지 사용자 행동을 처리하는 전용 서비스(`MovieRecordService`)에서 두 저장을 한 트랜잭션으로 묶는다.
- **TypeORM**: `dataSource.transaction(async (manager) => { … })`. 콜백이 정상적으로 끝나면 commit, 콜백에서 예외가 나면 rollback이다. **콜백 안에서는 `manager.getRepository(...)`로 꺼낸 Repository만** 쓴다. 평소에 주입받은 Repository를 섞어 쓰면 같은 트랜잭션 연결을 쓴다는 보장이 없다.
- **Spring과의 대응**: `@Transactional`을 서비스 메서드에 붙이면 메서드가 끝날 때 commit, 런타임 예외가 밖으로 나가면 rollback이다. 문법은 다르지만 "어느 하나라도 실패하면 앞선 저장을 남기지 않겠다"는 설계는 같다. (이번 실습은 NestJS로만 했고 Spring은 구현하지 않았다.)

**직접 확인한 것 (실제 MySQL, 일회용 DB)**

- `favorite` 테이블에 `BEFORE INSERT` 트리거(`SIGNAL SQLSTATE '45000'`)를 걸어 **즐겨찾기 저장만 실패하게** 만들고 `POST /movie-records`를 보냈다. 평점 INSERT는 이미 성공한 뒤인데도 응답은 500이고 **rating 행 0개, favorite 행 0개**였다. 방금 저장한 평점이 되돌아간 것이 rollback이다.
- 같은 상황에서 트랜잭션 없이 두 서비스를 연달아 부르는 "순진한 구현"은 **rating 행이 1개 남았다.** 사용자는 "평점과 즐겨찾기를 함께 저장"을 눌렀는데 평점만 저장된 상태다.
- 트랜잭션 래퍼만 지워도 이 두 테스트(롤백 증명, 경쟁 재현)가 실패했다.
- 이미 평점이 있는 영화로 같은 요청을 다시 보내면 409(`RATING409_1`)이고 **행 수가 늘지 않았다**(rating 1, favorite 1 그대로). 실패한 요청이 흔적을 남기지 않는다.

## commit / rollback

| | commit | rollback |
| --- | --- | --- |
| 뜻 | 봉투 안의 작업을 **최종 제출** | 봉투 안의 작업을 **처음 상태로 되돌림** |
| TypeORM에서 | 콜백이 정상 종료 | 콜백에서 예외 발생 |
| 이번 실습 | `POST /movie-records` 성공 → 평점과 즐겨찾기가 함께 저장 | 즐겨찾기 INSERT 실패 → 먼저 넣은 평점도 사라짐 |

- 서비스가 **먼저 검사하고 던지는** 오류(회원 없음 404, 평점 이미 있음 409)는 아직 아무것도 저장하기 전에 난다. rollback할 것이 없다. rollback이 의미 있는 것은 **저장 도중에** 난 오류(DB 오류, 동시 요청의 UNIQUE 위반)다.
- 저장 도중 DB 오류가 나면 응답은 500(`COMMON500`)이고 안쪽 DB 오류 문구는 응답에 나오지 않는다(전역 필터가 공통 틀로 바꾼다). 위 트리거 실험의 500이 그 경우다.

## 원자성(Atomicity)과 ACID

| 글자 | 뜻 | 이번 실습에서 본 것 |
| --- | --- | --- |
| **A**tomicity (원자성) | 전부 성공하거나 전부 취소 | 위 rollback 실험. 직접 확인했다 |
| **C**onsistency (일관성) | 트랜잭션 전후로 데이터 규칙이 지켜짐 | `(member_id, movie_id)` UNIQUE 제약이 같은 회원의 같은 영화 중복을 막는다. 제약을 위반한 INSERT는 거부되고 트랜잭션도 취소된다 |
| **I**solation (격리성) | 동시에 도는 트랜잭션이 서로 영향을 덜 주게 | 이 MySQL(InnoDB)의 기본 격리 수준이 `REPEATABLE-READ`, autocommit이 켜져 있다는 것까지만 확인했다. 격리 수준을 바꿔 가며 이상 현상(dirty read 등)을 일으켜 보지는 않았다 |
| **D**urability (지속성) | commit된 것은 장애가 나도 남음 | 개념으로만 정리했고 실험하지 않았다 |

- 원자성은 "트랜잭션을 쓰는 이유"이고, 격리성은 "동시 요청이 있어도 데이터가 안 깨지는 이유"의 일부다. 이번 동시성 실험(아래)은 격리 수준이 아니라 **UNIQUE 제약**이 최종 방어선이라는 것을 보여 준 것이다.
- 데드락은 이번 실험에서 관찰하지 못했다.

## UNIQUE 제약 조건 — 서버의 사전 검사와 DB 제약을 둘 다 두는 이유

`favorite`에는 `(member_id, movie_id)` **복합 UNIQUE**(`uk_favorite_member_movie`)가 있다. `movie_id`만 UNIQUE라면 한 영화가 서비스 전체에서 한 번만 즐겨찾기될 수 있으니, 반드시 두 값을 한 쌍으로 묶어야 한다.

| | 서버의 사전 검사 | DB UNIQUE 제약 |
| --- | --- | --- |
| 하는 일 | 저장하기 **전에** 이미 있는지 조회 | 저장할 때 같은 쌍이 있으면 **거부** |
| 목적 | 친절한 오류(`FAVORITE409_1`)와 불필요한 INSERT 줄이기 | **동시 요청까지 포함해** 데이터 자체를 지키는 마지막 안전망 |
| 약점 | 조회와 INSERT 사이에 다른 요청이 끼어들면 뚫림 | 오류 문구가 DB 언어(`ER_DUP_ENTRY`)라 그대로 보여 줄 수 없음 |

**직접 확인한 것**

- **서비스를 거치지 않고 SQL로** 같은 `(member_id, movie_id)`를 한 번 더 INSERT하면 DB가 거부했다. 사전 검사가 없어도 UNIQUE는 중복을 막는다.
- **같은 영화를 동시에 8번** 즐겨찾기했다. 보통은 사전 검사가 대부분 막아서 UNIQUE까지 가지 않는다. 그래서 8개 요청이 모두 사전 검사를 "없음"으로 통과할 때까지 서로 기다리게(배리어) 만들었다. 그 상태에서 결과는 **201 1개, 409 7개, DB 행 1개**이고 서버 경고 로그가 7건 남았다. 사전 검사를 모두 뚫어도 DB UNIQUE 하나만으로 한 건만 들어갔다.
- 그래서 필터가 `ER_DUP_ENTRY`(제약 이름 `uk_favorite_member_movie`)를 받아 사전 검사와 **같은 `FAVORITE409_1`**로 바꿔 준다. 사용자는 두 경우를 구분할 수 없다.
- 사전 검사를 지워 보면 **e2e 테스트는 못 잡고** 단위 테스트만 잡는다. 사전 검사가 없어도 같은 409가 필터를 통해 나오기 때문이다. "결과는 같고, 사전 검사는 메시지와 불필요한 INSERT를 위한 것"이라는 위 표의 설명과 맞는 결과다.
- 영화 기록에서도 평점이 저장되는 순간 다른 요청이 같은 즐겨찾기를 먼저 넣어 버리는 경쟁을 트리거로 재현했다. 결과는 409 `FAVORITE409_1`이고 **평점과 즐겨찾기 모두 취소**(행 0개)였다.

## 낙관적 잠금(Optimistic Locking)

> 이번 실습에서 구현하거나 실험하지 않았다. 개념 설명이다.

여러 요청이 **같은 행을 고치려 할 때** 충돌을 다루는 두 가지 방식이 있다.

| | 낙관적 잠금 | 비관적 잠금 |
| --- | --- | --- |
| 가정 | 충돌은 드물다 | 충돌이 잦을 수 있다 |
| 방법 | 행에 **버전 컬럼**을 두고, 저장할 때 "내가 읽은 버전 그대로인가"를 확인. 다르면 그 사이 누가 고친 것이라 **나중에** 실패시킴 | 읽을 때 행에 **잠금**(`SELECT … FOR UPDATE`)을 걸어 다른 요청을 기다리게 함 |
| 비용 | 평소엔 잠금이 없어 빠름, 충돌 시 재시도 필요 | 잠금 대기가 생김 |

- 이번 즐겨찾기 중복 문제는 "같은 행을 고치는 충돌"이 아니라 "같은 행이 **두 번 생기는** 문제"라서, 버전 컬럼이 아니라 **UNIQUE 제약과 트랜잭션**으로 풀었다.
- TypeORM에는 버전 컬럼(`@VersionColumn`)과 낙관적 잠금 옵션이 있다고 알고 있지만 이번에 써 보지 않았으므로, 동작을 확인한 뒤에 다시 정리할 부분이다.
