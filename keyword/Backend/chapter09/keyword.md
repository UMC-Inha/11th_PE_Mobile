# 9주차 백엔드 핵심 키워드

> 이 문서에서 **"직접 확인했다"**고 쓴 것은 이번 실습에서 실제로 실행해 본 것이고, 그렇지 않은 것은 개념 설명이다. Spring Boot(springdoc, JUnit, Mockito, H2)는 직접 써 보지 않았고 NestJS(`@nestjs/swagger`, vitest)로만 했다. 이 프로젝트는 워크북이 쓰는 Jest 대신 vitest를 쓴다(문법은 `describe`/`it`/`expect`로 거의 같다).

## Swagger / OpenAPI

**손으로 쓴 API 명세표는 코드가 바뀌는 순간 조용히 틀어진다.** 5주차에 만든 명세표는 7주차에 삭제 응답이 204에서 200으로, 요청에서 `memberId`가 사라졌을 때 같이 고쳐지지 않으면 거짓말이 된다. Swagger는 이 표를 **코드가 직접 만들게** 한다.

| 이름 | 정체 | 우리 프로젝트에서 |
| --- | --- | --- |
| **OpenAPI** | API를 설명하는 **규격**(JSON/YAML 형식). 기계가 읽는 문서 | `GET /api-docs-json` |
| **Swagger UI** | 그 JSON을 사람이 보기 좋게 그리고, 브라우저에서 바로 호출해 볼 수 있게 한 **화면** | `GET /api-docs` |
| `@nestjs/swagger` | NestJS의 컨트롤러·DTO를 읽어 OpenAPI JSON을 만드는 라이브러리 | `src/swagger/` + 컨트롤러·DTO의 데코레이터 |

- **코드에서 자동으로 읽는 것**: URL·Method, 경로 변수, 요청 DTO의 필드 이름. 라이브러리만 붙여도 15개 API가 전부 나타난다.
- **사람이 적어 줘야 하는 것**: 언제 부르는 API인지(`@ApiOperation`), 요청 예시(`@ApiBody`, DTO의 `@ApiProperty({ example })`), 성공·실패 응답의 모양(`@ApiResponse`), 토큰이 필요한지(`@ApiBearerAuth` → 자물쇠). 실패 응답의 모양은 우리 컨트롤러가 `{ isSuccess, code, message, result }` 객체를 그냥 만들어 돌려주기 때문에 타입 정보로 남지 않아서 직접 적어야 한다.
- **Authorize 버튼**: 토큰을 한 번 넣으면 자물쇠가 있는 모든 요청에 `Authorization: Bearer …`가 실린다. `Bearer ` 접두사는 문서 설정(`addBearerAuth`)이 "이 토큰은 Bearer 방식"이라고 알려 두었기 때문에 Swagger가 붙인다.
- **문서 데코레이터는 문서만 만든다.** 요청 검증(`ValidationPipe`)이나 오류 응답(`AllExceptionsFilter`)을 바꾸지 않는다. 이번에 문서를 붙인 뒤에도 "모르는 속성은 400"이 그대로인 것을 테스트로 확인했다.

**직접 확인한 것**

- 8주차에 "15개 API를 문서화했다"고 적었지만, `/api-docs-json`을 열어 표로 뽑아 보니 **평점·내 정보·회원가입·중복 확인 9개 API는 한 줄 요약과 자물쇠만 있고 설명이 0자**였고, 성공 예시가 없고 실패 응답은 401 하나뿐이었다. 9개를 채웠고 지금은 15개 모두 성공 예시와 그 API가 실제로 낼 수 있는 실패 응답의 상태 코드·`code` 예시가 있다.
- 문서의 실패 예시를 **실제 예외를 만드는 함수에서 그대로 뽑게** 했다(문서에 `"message": "…"`를 손으로 또 적지 않는다). 예외 문구를 바꾸면 문서도 같이 바뀐다.
- 그래도 문서가 코드와 어긋날 수 있어서 **문서의 예시를 실제 서버 응답과 비교하는 테스트**를 만들었다. 그 테스트가 정말 잡는지 문서를 일부러 틀리게 만들어 봤다: 예시 문구를 `5점`→`6점`으로 바꾸면 1개, `PATCH /ratings`의 403 문서를 지우면 3개, `DELETE /ratings`의 자물쇠를 지우면 2개 실패했다.
- 이 비교 테스트를 처음 만들 때 "문서에 그 예시가 없으면 빈 객체와 비교하고 통과"하게 짜서, 예시가 아예 없어도 초록불이 나왔다. 예시가 없으면 바로 실패하게 고쳤다(트러블슈팅).
- 같은 문서를 다시 훑자 8주차에 빠진 400 두 개(로그인 입력 오류, 숫자가 아닌 `movieId`로 즐겨찾기 해제)도 찾아서 채웠다.
- Spring의 `springdoc`(`@Tag`, `@Operation`, `@Schema`, `@SecurityRequirement`)은 같은 역할이다. 직접 써 보지 않았다.

## 단위 테스트(Unit Test)

**클래스 하나의 "판단"을 빠르게 확인하는 테스트.** 주로 Service가 대상이다. DB·HTTP·인증 같은 나머지는 **가짜(Mock/Stub)로 바꿔 끼운다.** 그래서 DB가 꺼져 있어도 돌고(우리 단위 143개가 약 2초) "이미 즐겨찾기한 경우 409를 던지는가" 같은 판단을 순식간에 확인할 수 있다.

- 알려 주는 것: **로직이 틀렸다.**
- 절대 못 잡는 것: URL 오타, 인증 설정 누락(`@UseGuards`를 빠뜨림), 요청 DTO 검증 규칙, 실제 DB의 UNIQUE·트랜잭션 동작. 이런 것은 진짜 요청을 흘려보내야 드러난다(다음 항목).
- 좋은 단위 테스트는 "저장되었는가"보다 **"저장하지 않았는가"**를 확인한다. 중복 검사를 깜빡 지워도 "정상 저장" 테스트는 통과하지만, "중복이면 저장하지 않는다"(`expect(save).not.toHaveBeenCalled()`) 테스트는 바로 빨간불이 켜진다.

**직접 확인한 것**

- `FavoriteService` 단위 테스트의 중복 검사 줄(`FAVORITE409_1`을 던지는 `if`)을 주석 처리하자 **1개가 실패**했다(`expected undefined to be an instance of ApiException`).
- `RatingService`의 중복 검사를 지우면 1개, 소유권(403) 검사를 지우면 3개가 실패했다. 6~7주차에 이미 있던 테스트가 정말 잡는지는 이번에 처음 확인한 것이다.
- 저장하는 척하는 것만 확인한 테스트는 의미가 약하다는 것도 보았다. `movie-record.service`의 `dataSource.transaction` 래퍼를 걷어 내면 이 서비스의 단위 테스트 **9개가 실패**했다(래퍼가 없으면 `manager`를 받는 콜백 모양이 달라지기 때문에, 이 9개는 "트랜잭션이 정말 되돌린다"는 증명이 아니라 "트랜잭션 모양으로 호출한다"는 확인이다).

## 통합 테스트(Integration Test)

**요청부터 응답까지 전체 흐름**을 확인하는 테스트. 컨트롤러·인증(`AuthGuard`)·입력 검증·Service·DB까지 **진짜**가 함께 돈다.

| | 단위 테스트 | 통합 테스트 |
| --- | --- | --- |
| 확인하는 것 | 클래스 하나의 판단(주로 Service) | 요청부터 응답까지 전체 흐름 |
| 함께 도는 것 | 없음(나머지는 가짜) | 컨트롤러, 인증, 검증, DB까지 진짜 |
| 속도 | 매우 빠름 | 느림 |
| 알려 주는 것 | 로직이 틀렸다 | **연결이 틀렸다** |

- **개발용 DB를 그대로 쓰면 안 된다.** 테스트를 돌릴 때마다 내 데이터에 쓰레기가 쌓이고, 이전 테스트가 남긴 데이터 때문에 다음 테스트가 실패하기도 한다. 워크북은 메모리 DB(H2, sql.js)를 쓰라고 하지만, 이 프로젝트는 **테스트 파일마다 이름이 `umc_movie_test_`로 시작하는 일회용 MySQL DB를 만들고 끝나면 지운다.** UNIQUE 제약·트랜잭션 rollback·동시 요청처럼 **진짜 MySQL에서만 드러나는 동작**을 확인해야 해서다. 대신 로컬 MySQL이 있어야 하고 느리다(통합 145개가 약 20~40초). 테스트 헬퍼는 이름이 `umc_movie_test`로 시작하지 않으면 `DROP`을 하기 전에 멈춘다.
- **테스트가 못 잡는 것도 있다.** 대표적으로 **CORS**는 브라우저가 스스로에게 거는 제약이라, 서버끼리 주고받는 테스트에서는 애초에 발생하지 않는다. 테스트가 초록불이어도 프론트와 연결할 때는 브라우저에서 한 번 확인해야 한다. 이번 주에는 브라우저에서 CORS를 새로 확인하지 않았다(8주차까지의 preflight 테스트만 그대로 통과).

**직접 확인한 것**

- 토큰 없이 `POST /ratings`는 401 `AUTH401_2`이고 **DB 행이 0개**, 토큰을 담아 보내면 201이고 **그 회원의 행이 1개**라는 통합 테스트 2개를 새로 만들었다.
- `POST /ratings`의 `@UseGuards(AuthGuard)`를 지우자 새 테스트 2개를 포함해 **18개가 실패**했다. 401 테스트 하나만 깨질 줄 알았는데, 가드가 없으면 `@LoginMember()`가 "가드를 빠뜨렸다"는 오류를 던져 `POST /ratings`를 쓰는 모든 테스트가 500이 되기 때문이다. 상태 코드를 201에서 200으로 바꾸면 16개가 실패했다.
- 같은 변이(`@UseGuards` 제거)에서 **단위 테스트 143개는 하나도 실패하지 않았다.** Service는 "누가 불렀는지"를 인자로 받을 뿐 가드가 붙어 있는지는 모르기 때문이다. 단위 테스트는 초록불인데 통합 테스트만 빨간불인, 표의 "로직이 틀렸다 vs 연결이 틀렸다"를 그대로 보여 준 사례다. 이 한 가지 말고 "연결이 틀렸다" 사례를 더 모으지는 못했다.

## Mock, Stub (그리고 Fake, Spy)

단위 테스트에서 진짜 DB 대신 끼워 넣는 가짜 객체를 통틀어 Mock이라고 부르기도 하지만, 엄밀하게는 역할이 다르다.

| 이름 | 하는 일 | 우리 테스트에서 |
| --- | --- | --- |
| **Stub** | 정해 둔 **답을 돌려준다.** "이 회원은 있다고 치자", "이미 즐겨찾기했다고 치자" | `exists: vi.fn().mockResolvedValue(true)` — 사전 검사가 "이미 있음"이라고 답하게 만든다 |
| **Mock** | 가짜가 **어떻게 불렸는지**를 확인한다 | `expect(favoriteRepository.save).not.toHaveBeenCalled()` — 저장을 시도하지 않았는지 |
| **Spy** | 진짜 동작은 두고 호출 기록만 몰래 본다 | `vi.spyOn(Logger.prototype, 'error')` — 에러 로그를 찍었는지 |
| **Fake** | 진짜처럼 **동작하는 가벼운 대체품** | (우리는 쓰지 않았다. 워크북의 메모리 DB가 여기에 해당) |

- 같은 `vi.fn()` 하나가 상황에 따라 Stub이면서 Mock이다(답을 정해 주고, 불린 횟수도 확인한다). 이름을 외우기보다 **"답을 정해 주려는가, 호출을 확인하려는가"**를 구분하는 것이 중요하다.
- **가짜는 상황을 마음대로 만든다**는 장점이 있다. 8주차의 "동시 8요청" 테스트는 사전 검사(`exists`)가 모두 "없음"으로 답하게(Stub) 만들어서, 실제로는 거의 못 만드는 "사전 검사를 뚫은 경쟁"을 재현했다.
- **가짜의 약점**: 가짜가 진짜와 다르게 행동하면 테스트는 초록불인데 진짜는 깨진다. 그래서 "트랜잭션이 정말 되돌아가는가"는 Mock이 아니라 **진짜 DB**(트리거로 INSERT를 실패시킴)로 확인했다.

## given-when-then

테스트를 **세 덩어리**로 적는 방식. Postman으로 확인할 때 머릿속으로 하던 "이런 상태에서(given) 이걸 누르면(when) 이게 나와야 해(then)"를 그대로 옮긴 것이다.

| 덩어리 | 하는 일 | 즐겨찾기 등록으로 예를 들면 |
| --- | --- | --- |
| given | 상황을 만든다 | 로그인한 회원이 있고, 이미 이 영화를 즐겨찾기했다 |
| when | 확인하고 싶은 **동작 하나**를 실행한다 | 즐겨찾기 등록을 호출한다 |
| then | 결과가 기대와 같은지 확인한다 | 409 `FAVORITE409_1`이고 저장 함수가 불리지 않았다 |

- **테스트 이름도 이 문장으로** 적으면 나중에 실패했을 때 무엇이 깨졌는지 이름만 읽어도 알 수 있다. 우리 테스트 이름: "토큰 없이 POST /ratings를 부르면 401 AUTH401_2이고 평점은 저장되지 않는다".
- when은 한 가지 동작이어야 한다. 한 테스트 안에서 요청을 여러 번 보내 시나리오를 이어 붙이면, 실패했을 때 어디서 깨졌는지 찾기 어렵다. (워크북 "Postman 시나리오" 테스트처럼 일부러 이어 붙인 것은 그 사실을 이름에 적었다.)
- `ratings.e2e-spec.ts`의 두 테스트에 `// given`, `// when`, `// then` 주석을 달았다.

## 회귀 테스트(Regression Test)

**"예전에 되던 게 지금도 되는가"**를 확인하는 테스트. 기능을 하나 고칠 때마다 Postman을 열어 15개 API를 하나씩 눌러 볼 수는 없으므로, 한 번 확인한 것을 테스트로 적어 두고 명령어 하나(`npm test && npm run test:e2e`)로 전부 다시 확인한다. 코드를 고칠 용기는 대체로 여기서 나온다. 고쳐도 무엇이 깨지는지 바로 알 수 있으면 리팩터링이 무섭지 않다.

**테스트도 틀릴 수 있다 — 일부러 깨뜨려 보는 이유 (변이 검사)**

테스트가 통과한다는 사실과 **"그 테스트가 지키려던 것을 정말 지키고 있다"**는 사실은 다르다. 그래서 코드를 일부러 망가뜨리고 테스트가 빨간불이 되는지 본다(이런 기법을 변이 테스트, mutation testing이라고 부른다. 이번에는 사람이 손으로 몇 가지만 해 봤다).

| 지운 것 | 단위 | 통합 |
| --- | --- | --- |
| 즐겨찾기 중복 사전 검사 | 1개 실패 | **0개 실패** |
| 사전 검사 + DB UNIQUE→409 변환 | 1개 실패 | 5개 실패 |
| 영화 기록의 트랜잭션 | 9개 실패 | 2개 실패 |
| 평점 중복 사전 검사 | 1개 실패 | **0개 실패** |
| 평점 소유권(403) 검사 | 3개 실패 | 4개 실패 |
| `POST /ratings`의 `AuthGuard` | **0개 실패** | 18개 실패 |

이번 실험에서 알게 된 것 (**직접 확인한 것**):

1. **사전 검사를 지워도 통합 테스트는 초록불이다.** 두 번째 방어선인 DB UNIQUE 제약과, 그 위반을 같은 409로 바꾸는 예외 필터가 결과를 같게 만들어서다. 사용자에게 가는 응답은 그대로이고, 사전 검사가 지켜 주던 "불필요한 INSERT를 시도하지 않는다"는 점은 **단위 테스트만** 잡는다. 두 방어선을 모두 지워야 통합 테스트가 실패한다. 한 종류의 테스트로는 모든 걸 잡지 못한다는 것을 보여 주는 사례다.
2. **워크북의 선택 미션 시나리오(이미 즐겨찾기한 영화에 `addToFavorites: true`)는 트랜잭션을 증명하지 못한다.** 사전 검사가 평점을 저장하기 **전에** 먼저 막아서, 트랜잭션을 걷어 내도 이 테스트는 통과한다. 트랜잭션을 정말 증명하는 것은 "평점 INSERT가 성공한 뒤 즐겨찾기 INSERT가 DB에서 실패하게 만들어" 두 테이블이 0행인지 세는 테스트이고, 트랜잭션을 걷어 내자 그 테스트와 경쟁 상황 테스트 2개가 실패했다.
3. **실패 줄은 읽을 가치가 있다.** 예를 들어 트랜잭션을 걷어 내자 `expected { rating: 1, favorite: +0 } to deeply equal { rating: +0, favorite: +0 }`가 나왔다. 평점이 1행 남았다는 것을 한 줄로 알려 준다.

## 개념으로만 정리한 것

- **TDD**(테스트를 먼저 쓰는 개발)와 **테스트 커버리지**(테스트가 지나간 줄의 비율)는 이번에 쓰지 않았다. 커버리지 수치는 "줄이 실행되었다"일 뿐 "그 줄이 맞는지 확인했다"가 아니라는 것을 위 변이 실험이 보여 준다(사전 검사 줄은 통합 테스트가 실행하지만 지워도 통과했다).
- **E2E 테스트**와 이번 "통합 테스트"의 경계: 우리는 프론트(앱)를 거치지 않고 서버의 HTTP 요청부터 DB까지만 검증했다. 앱 화면까지 포함한 End-to-End는 프론트 쪽 미션에서 실제 서버에 붙여 확인했다.
