# 7주차 백엔드 핵심 키워드

## 인증(Authentication)과 인가(Authorization)

| | 인증 | 인가 |
| --- | --- | --- |
| 질문 | 너 누구야? | 너 이거 해도 돼? |
| 시점 | 로그인할 때 한 번, 이후엔 토큰으로 요청마다 확인 | 요청마다 |
| 수단 | 이메일 + 비밀번호(토큰은 그 결과물) | 토큰이 알려 준 신원 + 서버의 검사 |
| 실패 | **401 Unauthorized** | **403 Forbidden** |
| 이 프로젝트에서 | `AuthGuard` (컨트롤러 앞) | `RatingService.findOwnedRating` (DB를 본 뒤) |

- 이름 때문에 401이 "인가 실패"처럼 보이지만, 401은 **인증 실패**("누군지 모르겠다")이고 403이 **인가 실패**("누군지는 알지만 그건 네 것이 아니다")다.
- 인증은 모든 보호 API가 똑같이 거치는 일이라 **공통 관문(Guard)** 에서 한 번에 처리한다. 인가는 "이 평점이 내 것인가"처럼 **DB를 조회해 봐야 아는 기능별 규칙**이라 서비스가 처리한다. 관문이 신원까지만 확인하고 소유권은 모른다.
- 이 서비스에는 관리자·VIP 같은 등급이 없어서 인가는 "내가 쓴 것인가" 하나뿐이다.
- **404와 403의 순서**: 평점을 먼저 찾고(없으면 404) 찾았을 때 주인을 본다(내 것이 아니면 403). 반대로 하면 존재하지도 않는 평점에 "권한이 없다"고 답하게 된다. 소유자 검사를 지우면 e2e 테스트 2개가 실패하는 것을 확인했다.
- 403은 "그 번호의 평점이 존재한다"는 사실을 알려 주는 부작용이 있어서, 서비스에 따라 남의 것에도 404를 돌려 존재를 숨기기도 한다. 이번 실습은 401·403의 차이를 눈으로 보는 것이 목적이라 403을 그대로 썼다.
- memberId를 요청에서 받으면 `memberId`를 2로 바꿔 보내는 것만으로 남의 평점을 만들고 고치고 지울 수 있다. 값을 **받지 않는 것**이 그 값을 조작당하지 않는 방법이다. 그래서 `POST /members/{memberId}/ratings`가 `POST /ratings`로 짧아졌다. 요청 Body에 `memberId`를 몰래 넣어도 400(`property memberId should not exist`)으로 거절되고, 6주차 경로는 404다.

## 해시, salt, bcrypt: 로그인에서 비밀번호를 비교하는 방법

비밀번호는 해시(단방향)로 저장하므로 원문으로 되돌릴 수 없다. 그래서 로그인에서는 되돌리는 대신 **입력값을 같은 방식으로 해시해서 비교**한다.

- `$2b$10$` + salt 22자 + 해시 31자. salt와 cost가 해시 문자열 안에 들어 있어서 `bcrypt.compare(입력값, 저장된 해시)` 한 번이면 salt를 꺼내 같은 방식으로 계산한 뒤 비교한다.
- salt가 매번 달라도 비교할 수 있는 이유가 이것이다. 같은 비밀번호를 쓰는 두 회원의 해시는 서로 다르다.
- **로그인 실패는 원인이 무엇이든 하나로 합친다.** "없는 이메일"과 "틀린 비밀번호"를 나눠서 알려 주면 공격자가 이메일을 하나씩 넣어 보며 가입 여부를 알아낼 수 있다. 두 경우 모두 `AUTH401_1`과 같은 문구를 돌려주고, 응답 본문이 글자까지 같은 것을 e2e와 Newman에서 비교로 확인했다.
- **응답 시간도 새어 나간다.** 본문을 같게 만들었는데도, 이메일이 없으면 bcrypt 비교(cost 10, 수십 ms)를 건너뛰어 훨씬 빨리 응답한다. 이 Mac에서 재 보니 틀린 비밀번호 75.9ms, 없는 이메일 1.7ms로 약 44배 차이였다. 없는 이메일에도 가짜 bcrypt 해시와 `compare`를 한 번 실행하게 하자 57.8ms 대 57.5ms로 비슷해졌다. (같은 머신에서 15회 중앙값을 본 것이라, 네트워크와 부하가 있는 환경의 통계적 차이까지 없앴다고 말할 수는 없다.)
- 로그인 DTO는 비밀번호 **형식**(대·소문자·숫자·특수문자)을 검사하지 않는다. 규칙이 바뀌기 전에 가입한 회원이 로그인조차 못 하게 되기 때문이다. 이메일 형식과 "비어 있지 않음"만 본다.

## JWT (Header / Payload / Signature, Claim)

점으로 나뉜 세 덩어리 문자열이다.

| 부분 | 내용 | 이번 토큰의 실제 값 |
| --- | --- | --- |
| Header | 서명 알고리즘 | `{"alg":"HS256","typ":"JWT"}` |
| Payload | Claim들 | `{"sub":"3","email":"viewer1@umc.com","iat":…,"exp":…}` |
| Signature | Header·Payload를 비밀키로 서명한 값 | (가림) |

- **Claim**: `sub`(subject, 토큰의 주인 = 회원 번호), `iat`(발급 시각), `exp`(만료 시각, 초 단위). 만료 시각이 토큰 안에 있어서 서버가 아무것도 기억하지 않고도 만료를 판정한다. 이번 토큰은 `exp − iat = 3600`초였다.
- **Payload는 암호화가 아니라 인코딩(Base64URL)이다.** 비밀키 없이도 누구나 읽을 수 있다. 실제로 발급받은 토큰의 Header·Payload를 디코드해서 읽었다. 그래서 비밀번호·주민번호처럼 남이 보면 안 되는 값은 넣지 않는다. 서명이 지켜 주는 것은 "내용을 몰래 바꿀 수 없다"는 위조 방지이지 "내용을 못 본다"는 기밀성이 아니다.
- **서명 검증**: 서버는 받은 Header·Payload를 자기 비밀키로 다시 서명해 보고, 토큰에 실려 온 Signature와 다르면 거절한다. 비밀키를 모르면 유효한 서명을 만들 수 없다. Payload의 글자 하나를 다른 글자로 **교체**하면 `AUTH401_3`(유효하지 않은 토큰)이 나온다. 서명을 검증하지 않고 디코드만 하도록 코드를 바꿔 보면 e2e 테스트 3개가 실패하는 것도 확인했다.
- 토큰 맨 뒤에 글자를 **덧붙이는** 방식으로 변조를 시도하면 Base64 자투리가 버려져 통과할 수 있다는 설명이 있었다. 이 서버(`jsonwebtoken`)에서는 덧붙인 토큰도 거절됐다. 교체 방식이 확실한 검증 방법이다.
- **HS256은 256비트(32바이트) 이상의 키**를 요구한다. 그래서 `JWT_SECRET`이 없거나 32자보다 짧거나, `.env.example`의 예시 값 그대로면 **서버가 시작되지 않게** 했다. 약한 키로 조용히 뜨는 것보다 시작을 막는 편이 낫다. 알고리즘도 HS256으로 고정해 헤더의 `alg`를 바꿔 끼우는 공격을 처음부터 막았다.
- 비밀키를 아는 사람은 누구나 원하는 내용으로 토큰을 만들 수 있다. 그래서 코드에 쓰지 않고 `.env`로 관리하며 Git에 올리지 않는다. 변경한 파일 전체에서 실제 키가 없는지 검색했다.
- **한계**: 토큰은 한 번 발급하면 만료 전까지 취소하기 어렵다(로그아웃·폐기·Refresh Token은 이번 범위 밖).

## Bearer 인증과 Authorization 헤더

```http
GET /members/me
Authorization: Bearer eyJhbGciOiJIUzI1NiIs…
```

- HTTP 요청은 헤더(어떻게 다룰지)와 바디(무엇을 보낼지)로 되어 있다. 토큰은 "무엇을 하려는가"가 아니라 "**누가** 하려는가"에 대한 정보라서 헤더에 싣는다.
- **GET과 DELETE는 바디를 쓰지 않는 것이 관례**라서, 바디에 토큰을 담으면 조회·삭제 API에서 토큰을 보낼 방법이 없다. 헤더는 모든 메서드에 붙일 수 있다.
- `Bearer`는 "이 토큰을 지참한 사람"이라는 표준 표기이고 뒤에 **띄어쓰기 한 칸**이 있다. 토큰을 꺼낼 때 이 접두사를 잘라 내야 한다. 이 서버는 `bearer`/`BEARER`처럼 대소문자가 달라도 받고, `Bearer ` 뒤가 비어 있으면 토큰이 없는 것으로 본다(`AUTH401_2`).
- 6주차까지는 URL과 바디만 맞추면 됐는데, 이번 주차부터 갑자기 401이 돌아오면 URL이나 바디보다 **헤더부터** 확인한다.

## Guard (NestJS) / HandlerInterceptor (Spring)

컨트롤러가 실행되기 **전에** 요청을 들여보낼지 결정하는 관문이다. 토큰 검사를 컨트롤러마다 복사하면 API가 20개일 때 20번 복사하고, 하나라도 빠뜨리면 그 API만 문이 열린다. 건물 로비에 게이트 하나를 세우는 것과 같다.

| | NestJS `AuthGuard` | Spring `HandlerInterceptor` |
| --- | --- | --- |
| 적용 방식 | `@UseGuards(AuthGuard)`를 **붙인 곳만** (열린 상태에서 하나씩 잠금) | 워크북 설명 기준으로, 전체를 잠그고 예외 경로를 연다 |
| 실패 처리 | `ApiException`을 던지면 전역 필터가 `{isSuccess, code, message, result}`로 바꿈 | 비슷하게 예외 처리기 |
| 신원 전달 | 요청 객체에 `memberId`를 담아 둠 | `request.setAttribute` |

- NestJS는 **빠뜨리기 쉬운 쪽**이다. 새 API를 만들 때 `@UseGuards`를 붙이지 않으면 아무도 알려 주지 않는다. 그래서 보호 대상 5개 라우트(`GET·PATCH /members/me`, `POST /ratings`, `PATCH·DELETE /ratings/:id`)가 모두 토큰 없이 401을 내는지를 e2e로 확인한다. 삭제 API의 `@UseGuards`를 지우면 e2e가 2개 실패하는 것을 확인했다.
- 공개 API인 `GET /members/:memberId/ratings`는 Guard를 붙이지 않는다. "특정 회원이 남긴 평점"은 누구나 볼 수 있는 기능이다.
- **Guard가 하는 일 세 가지**: ① `Authorization` 헤더에서 토큰을 꺼내고 ② 서명·만료를 검증해 회원 번호를 알아내고 ③ 그 번호를 요청에 담는다. 그 덕분에 컨트롤러는 토큰이 뭔지 몰라도 `memberId`만 받아 쓰면 된다.
- 만료(`AUTH401_4`)는 다시 로그인하면 해결되는 상황이라 위조·변조(`AUTH401_3`)와 구분한다. 토큰이 없는 `AUTH401_2`와 코드가 달라서, 응답만 보고도 프론트가 "로그인 화면으로 보낼지, 다시 로그인을 안내할지" 정할 수 있다.
- **`createParamDecorator`로 반복 줄이기(선택 2)**: 컨트롤러마다 `@Req() request` + `request['memberId']`를 쓰던 것을 `@LoginMember() memberId`로 줄였다. 키 문자열은 Guard와 데코레이터가 같이 쓰는 상수 한 곳에만 있다. Guard 없이 쓰면 조용히 `undefined`를 주지 않고 오류를 던져 개발 실수를 드러낸다.
- 워크북의 `request['memberId']`는 이 프로젝트의 strict 설정에서 `TS7053`으로 컴파일되지 않았다(요청 타입에 그 속성이 없어서). 요청 타입을 확장한 `AuthenticatedRequest`와 키 상수로 풀었고, 데코레이터를 만들면서 컨트롤러에서 문자열 키 자체가 사라졌다.

## 401 Unauthorized와 403 Forbidden의 차이

| 상황 | 상태 | code | 서버가 아는 것 |
| --- | --- | --- | --- |
| 헤더가 없음 | 401 | `AUTH401_2` | 요청자를 특정할 수 없다 |
| 토큰 변조 | 401 | `AUTH401_3` | 특정할 수 없다(서명 불일치) |
| 토큰 만료 | 401 | `AUTH401_4` | 한때 누구였는지는 알지만 지금은 확인 불가 |
| 로그인 정보 틀림 | 401 | `AUTH401_1` | 이메일·비밀번호 중 어느 쪽이 틀렸는지는 일부러 알려 주지 않는다 |
| 남의 평점을 수정·삭제 | **403** | `RATING403_1` | **요청자는 안다. 그 데이터가 남의 것이다** |
| 없는 평점 | 404 | `RATING404_1` | 대상이 없다 |

- **토큰은 멀쩡한데 막히는 것**이 403이다. 인증은 통과했고 인가에서 걸린 것이다. 프론트 입장에서 401은 로그인 화면으로 보내야 하고, 403은 "권한이 없습니다"를 안내해야 해서 반드시 구분되는 정보여야 한다.
- 코드 이름은 `{도메인}{HTTP 상태}_{일련번호}`(`AUTH401_4`)로 지어서, 이 코드만 보고도 "인증에서 401이 났고 그중 네 번째 사유"임을 알 수 있다. 6주차에는 실패가 몇 종류 되지 않아 `MEMBER4091` 정도로 충분했지만 401만 네 가지가 되자 사유를 구분할 필요가 생겼다.
- **204 대신 200**: 6주차 평점 삭제는 204(본문 없음)였다. 204는 본문을 보내지 않겠다는 뜻이라 우리가 약속한 `{isSuccess, code, message, result}`를 실을 수 없다. 삭제만 틀에서 빠지는 것을 막으려고 200으로 맞추고 `result`에 `null`을 담았다. 상태 코드의 규칙과 프로젝트의 응답 규칙이 충돌할 때 어느 쪽을 왜 택했는지 알고 있어야 한다.
- `/auth/login`은 원칙(URL은 명사)에서 벗어난 예외다. `POST /auth/tokens`("토큰이라는 자원을 만든다")가 더 정확하지만, 로그인·로그아웃을 `/login`, `/logout`으로 쓰는 서비스가 워낙 많아 한눈에 알아보는 이점을 택했다. 원칙에서 벗어난 예외라는 것을 알고 쓰는 것과 모르고 쓰는 것은 다르다.
