# Chapter 05 키워드 정리

## 1. SOP와 CORS

SOP는 동일 출처 정책으로, 한 출처의 JavaScript가 다른 출처의 응답을 읽지 못하게 막는 브라우저의 기본 보안 규칙임. 출처는 프로토콜, 호스트, 포트의 조합이라 localhost:5173과 localhost:8081도 다른 출처로 취급됨. CORS는 서버가 Access-Control-Allow-Origin 응답 헤더로 특정 출처를 허용해 이 제한을 풀어주는 방법임. 요청은 서버까지 도착하고, 브라우저가 응답 헤더를 확인한 뒤 JS에 전달할지 결정함. 따라서 CORS 에러는 프론트가 아니라 서버 설정으로 해결해야 함.

---

## 2. Same-Origin과 Same-Site의 차이

Same-Origin은 프로토콜, 호스트, 포트가 모두 같아야 하는 엄격한 기준임. Same-Site는 프로토콜과 umc.com 같은 등록 가능 도메인만 같으면 되는 느슨한 기준임. 그래서 api.umc.com과 www.umc.com은 Cross-Origin이지만 Same-Site임. Same-Origin은 응답을 JS가 읽을 수 있는지 판단할 때, Same-Site는 요청에 쿠키를 실어 보낼지 판단할 때 쓰임.

---

## 3. 쿠키의 SameSite 속성

SameSite는 다른 사이트에서 시작된 요청에 쿠키를 보낼지 정하는 속성으로, 주로 CSRF 공격을 막는 데 쓰임. Strict는 같은 사이트 요청에만 쿠키를 보냄. Lax는 여기에 더해 외부 링크로 이동하는 GET 요청에도 보내며, 값을 지정하지 않았을 때 브라우저가 쓰는 기본값임. None은 모든 요청에 쿠키를 보내고, HTTPS에서만 쿠키를 보내게 하는 Secure 속성과 반드시 함께 써야 함.

---

## 4. 복합 UNIQUE 제약을 사용하는 이유

복합 UNIQUE는 여러 컬럼의 조합이 중복되지 않게 막는 제약임. member_id와 movie_id 조합에 걸면 한 회원이 같은 영화를 두 번 등록하는 것만 막고, 다른 영화를 등록하거나 다른 회원이 같은 영화를 등록하는 것은 허용함. 컬럼마다 따로 UNIQUE를 걸면 한 회원이 영화를 하나만 등록할 수 있게 되어 요구사항과 맞지 않음. 코드에서 중복을 확인하는 방식은 요청이 동시에 들어오면 뚫릴 수 있어서, DB 제약으로 최종 보장하는 것이 안전함.

---

## 5. API Key는 프론트/백엔드 중 어디에 둬야 하나

비밀이어야 하는 API Key는 백엔드에 둬야 안전함. 프론트 코드는 사용자 브라우저로 내려가기 때문에 개발자 도구로 키를 쉽게 볼 수 있고, .env에 넣어도 빌드할 때 JS 파일에 그대로 들어감. 백엔드가 키를 붙여 외부 API를 대신 호출하면 키가 노출되지 않고, 호출 횟수 제한이나 캐싱도 서버에서 할 수 있음. 지도 API처럼 브라우저에서 쓰도록 만든 키는 허용 도메인을 제한하는 방식으로 보호함.
